# Go memory model

Документ go.dev/ref/mem отвечает на один вопрос: **при каких условиях чтение переменной в одной горутине гарантированно увидит запись из другой**. Пересмотрен в июне 2022 (Go 1.19), тогда же атомики получили формальную семантику.

Связанные заметки: [[atomic]], [[channels]], [[mutex]], [[once]], [[waitgroup]], [[cache coherence]].

## Совет номер один

Из документа дословно: *«Programs that modify data being simultaneously accessed by multiple goroutines must serialize such access. Don't be clever.»* Если нужно рассуждать о модели памяти, чтобы понять, корректна ли программа, программа скорее всего написана неправильно. Используй каналы и `sync`.

## Гонка данных

*Data race*: два обращения к одной переменной из разных горутин, хотя бы одно из них запись, и они не упорядочены отношением *happens-before*. Программа с гонкой некорректна. Детектор `go test -race` и `go run -race` ловит их на этапе выполнения через алгоритм ThreadSanitizer.

В отличие от C++, Go не объявляет гонку полным неопределённым поведением: чтение слова размером с машинное вернёт какое-то из ранее записанных значений, а не мусор из воздуха. Но многословные значения (`interface`, `string`, слайс) могут прочитаться разорванными: заголовок от одной записи, данные от другой. Это уже путь к крашу.

## Happens-before

Частичный порядок над событиями программы. Запись `w` видна чтению `r`, если `w` *happens before* `r` и нет другой записи в ту же переменную между ними. Внутри одной горутины порядок совпадает с порядком в коде. Между горутинами его создают только операции синхронизации. Без них компилятор и процессор вправе переставлять инструкции, а кеши вправе показывать разным ядрам разные значения. См. [[cache coherence]].

## Правила синхронизации

**Горутины**
- Оператор `go` *happens before* начало выполнения горутины.
- Завершение горутины **не** синхронизировано ни с чем. «Она же уже закончилась» ничего не гарантирует без явной синхронизации.

**Каналы** (см. [[channels]])
- Отправка *happens before* завершение соответствующего приёма.
- `close` *happens before* приём нулевого значения из-за закрытия.
- Приём из **небуферизованного** канала *happens before* завершение отправки. Поэтому небуферизованный канал синхронизирует в обе стороны.
- Для канала ёмкости C: k-й приём *happens before* завершение (k+C)-й отправки. Так буферизованный канал работает как [[semaphore]].

**sync**
- `Mutex`, `RWMutex`: n-й `Unlock` *happens before* (n+1)-й `Lock`. Для `RLock` после n-го `Unlock` соответствующий `RUnlock` *happens before* (n+1)-й `Lock`.
- `Once`: завершение `f` *happens before* возврат любого `Do`. См. [[once]].
- `WaitGroup`: `Done` *happens before* возврат `Wait`, это документировано в пакете. См. [[waitgroup]].
- `sync.Cond`, `sync.Map`, `sync.Pool`: свои гарантии в документации пакета.

**Атомики**
- Все операции `sync/atomic` **последовательно согласованы**: существует единый глобальный порядок всех атомарных операций, согласованный с порядком в каждой горутине. Это как `seq_cst` в C++. Атомарная запись *synchronizes before* атомарное чтение, которое её увидело. См. [[atomic]].

**Инициализация**
- Инициализация пакета *happens before* `main.main`. Импортируемый пакет инициализируется раньше импортирующего.

**Финализаторы**
- `SetFinalizer(x, f)` *happens before* вызов `f(x)`.

## Что это значит на практике

Классическая ошибка:

```go
var a string
var done bool

go func() { a = "hello"; done = true }()
for !done {}
print(a)
```

Здесь нет ни одного правила синхронизации между горутинами. Компилятор вправе вынести чтение `done` из цикла (бесконечный цикл), процессор вправе показать `done == true` раньше `a`. Замена `done` на `atomic.Bool` чинит обе проблемы: атомарная запись после `a = "hello"` и атомарное чтение, которое её увидело, дают happens-before, а с ним и видимость `a`.

Тот же механизм заставляет работать быстрый путь [[once]] через одно атомарное чтение и проверку `Load == done` в [[mutex|мьютексе на futex]].

## Что модель не обещает

- Порядок между **не**синхронизированными горутинами. Наблюдать «переставленные» записи с другого ядра это норма, а не баг железа.
- Что гонка проявится. Тесты могут проходить годами, а сломаться на другой архитектуре или другой версии компилятора. Поэтому `-race` в CI обязателен.
