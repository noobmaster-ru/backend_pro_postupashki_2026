# Когерентность кешей

У каждого ядра свой кеш L1 и L2, а память общая. Протокол когерентности гарантирует, что все ядра видят **одну и ту же последовательность записей в каждую отдельную ячейку**. Он же объясняет, почему атомики и замки под конкуренцией дорогие, и почему [[spinlock|TTAS]] быстрее наивного спинлока.

Связанные заметки: [[spinlock]], [[atomic]], [[go memory model]], [[rwmutex]], [[sync.Mutex internals]].

## Кеш-линия

Единица обмена между кешем и памятью. На x86 и большинстве ARM это **64 байта**, на Apple M-серии 128. Процессор не читает и не пишет отдельные байты в память, только целые линии. Поэтому две переменные, лежащие рядом, для протокола когерентности **одна и та же вещь**.

## MESI

Каждая линия в каждом кеше находится в одном из четырёх состояний:

| Состояние | Смысл |
|---|---|
| **M**odified | линия изменена только в этом кеше, память устарела; только этот кеш ей владеет |
| **E**xclusive | линия только в этом кеше и совпадает с памятью; писать можно без переговоров |
| **S**hared | линия есть в нескольких кешах, все копии чистые; читать можно, писать нельзя |
| **I**nvalid | копия недействительна |

Правила, которые важны для программиста:

- **Читать** можно из S и E. Несколько ядер держат одну линию в S одновременно и читают её без единого сообщения по шине.
- **Писать** можно только из M или E. Чтобы записать в линию в состоянии S, ядро рассылает *invalidate* всем остальным, дожидается подтверждений, переводит свою копию в M. Это называется *read for ownership* (RFO) и стоит десятки–сотни тактов.
- Когда другое ядро хочет прочитать линию в состоянии M, владелец обязан отдать данные и перейти в S.

Расширения: MOESI (AMD, состояние Owned позволяет делиться грязной линией без записи в память), MESIF (Intel, Forward назначает одного ответчика среди Shared). Суть та же.

## Cache line bouncing

Два ядра по очереди пишут в одну линию. Каждая запись: invalidate соседу, RFO, переход в M. Линия «скачет» между ядрами, и каждый прыжок это обмен сообщениями через межъядерную сеть с латентностью 40–100 нс. Полезная работа в это время не делается.

Именно это происходит:
- с наивным спинлоком, где все ждущие крутят CAS, то есть **пишут**. TTAS чинит это чтением в состоянии S, см. [[spinlock]];
- со счётчиком читателей в [[rwmutex]]: каждый `RLock` и `RUnlock` это запись в общее слово, поэтому при коротких секциях RWMutex проигрывает обычному мьютексу;
- с любым общим атомарным счётчиком, который инкрементят все горутины. Лечится шардированием: у каждого P свой счётчик, сумма считается редко.

## False sharing

Две **независимые** переменные лежат в одной линии. Ядро A пишет в первую, ядро B во вторую, логически они не конфликтуют, но протокол работает на уровне линий, и они мешают друг другу ровно так же, как если бы писали в одно слово.

```go
type Counters struct {
    a uint64 // ядро A
    b uint64 // ядро B — та же линия, что и a
}
```

Лечение: выравнивание на границу линии, чтобы каждая горячая переменная жила в своей.

```go
type Counters struct {
    a uint64
    _ [56]byte // добить до 64 байт
    b uint64
    _ [56]byte
}
```

В `golang.org/x/sys/cpu` есть `CacheLinePad` нужного размера под текущую архитектуру. Рантайм Go так же раскладывает структуры `p` и `mheap`, поля `pad` там именно для этого. Диагностика: `perf c2c` на Linux показывает линии, за которые дерутся ядра.

## Когерентность и модель памяти это разные вещи

Когерентность гарантирует порядок записей **в одну ячейку**. Она ничего не говорит о порядке записей **в разные ячейки**, как их увидит другое ядро. Между ядром и его кешем стоят буфер записи (*store buffer*) и очередь инвалидаций (*invalidate queue*), из-за которых запись в `a` может стать видна позже записи в `b`, хотя в коде она раньше.

Поэтому кроме когерентности нужны барьеры памяти (`mfence` на x86, `dmb` на ARM), и поэтому язык определяет [[go memory model]]: какие операции создают happens-before. Атомики Go компилируются с нужными барьерами, обычные записи нет.

x86 даёт сильную модель TSO: единственная разрешённая перестановка это «загрузка после сохранения». ARM и RISC-V слабые: без барьеров переставляется почти всё. Код с гонкой, работающий на x86, ломается на ARM, это частая история при переезде на Apple Silicon или Graviton.

## Практические следствия для Go

- Горячие счётчики шардировать по P или по горутине, суммировать редко.
- Не класть мьютекс и защищаемые им данные, которые читают без замка, в одну линию с полями, в которые часто пишут.
- Короткие критические секции под конкуренцией: обычный `sync.Mutex` вместо RWMutex.
- Чтение без замка через `atomic.Pointer` на неизменяемую структуру, см. [[RCU]]: читатели держат линию в S и никому не мешают.
- Не полагаться на «на моей машине работает»: `-race` в CI и тесты на ARM.
