# Futex

*Fast Userspace muTEX*, системный вызов Linux, появившийся в 2.6 (2003, Franke, Russell, Kirkwood). Идея: замок живёт в обычной памяти процесса, все быстрые пути делаются атомиками без ядра, а ядро подключается только для того, чтобы **уснуть** и **разбудить**. На futex построены `pthread_mutex`, `pthread_cond`, семафоры glibc, парковка потоков рантайма Go и всё, что в этом хранилище: [[mutex]], [[semaphore]], [[waitgroup]], [[once]], [[rwmutex]], [[barrier]].

Связанные заметки: [[mutex]], [[atomic]], [[goroutine scheduler]], [[spinlock]].

## Интерфейс

```c
long futex(uint32_t *uaddr, int op, uint32_t val,
           const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3);
```

Две основные операции:

| Операция | Что делает |
|---|---|
| `FUTEX_WAIT(addr, val)` | если `*addr == val`, усыпить вызывающего в очереди на этом адресе; иначе вернуть `EAGAIN` сразу |
| `FUTEX_WAKE(addr, n)` | разбудить до `n` спящих на адресе; `n = 1` одного, `INT_MAX` всех |

Флаг `FUTEX_PRIVATE_FLAG` говорит, что адрес не разделяется между процессами, и ядро может не искать его по физической странице. Это быстрее, и именно так работает `internal/futex` в домашке.

Проверка `*addr == val` и засыпание делаются **атомарно под замком ядра**. Это единственное, ради чего нужно ядро: пользовательский код не может «проверить и уснуть» неделимо. Без этого возможна потерянная побудка: между проверкой и сном кто-то сделал Wake, и поток спит вечно.

## Как устроено в ядре

- Хеш-таблица корзин (`futex_hash_bucket`), ключ вычисляется из адреса. Для приватных futex это `mm + виртуальный адрес`, для разделяемых физическая страница и смещение.
- В каждой корзине спинлок и список ждущих (`futex_q`), каждый с указателем на задачу.
- `WAIT`: взять спинлок корзины, прочитать `*uaddr`, сравнить с `val`, при совпадении встать в очередь и уснуть, отпустив спинлок.
- `WAKE`: взять спинлок корзины, пройти по очереди, разбудить до `n` задач с тем же ключом.

Никакого состояния «этот futex захвачен» в ядре нет. Ядро хранит только очереди спящих. Что означают значения в слове, решает пользовательский код. Поэтому одним и тем же syscall'ом собираются и мьютекс, и семафор, и барьер.

## Почему возвращаться из Wait надо в цикле

`FUTEX_WAIT` возвращается, когда:
- значение не совпало (`EAGAIN`), это нормальный путь;
- кто-то сделал `WAKE`;
- пришёл сигнал (`EINTR`);
- истёк таймаут.

Ни в одном случае не гарантируется, что условие, которого ждали, наступило. Разбудить могли лишнего, или условие уже снова нарушено. Правило: после `Wait` всегда перечитать состояние и при необходимости уснуть снова. Все примитивы в хранилище так и делают.

## Расширенные операции

- `FUTEX_WAIT_BITSET`/`FUTEX_WAKE_BITSET`: маска, чтобы будить подмножество ждущих на одном адресе.
- `FUTEX_REQUEUE`/`FUTEX_CMP_REQUEUE`: переставить спящих с одного адреса на другой без пробуждения. Нужна для `pthread_cond_broadcast`: ждущих на условной переменной переносят в очередь мьютекса, вместо того чтобы будить всех и заставить драться за него.
- `FUTEX_LOCK_PI`/`FUTEX_UNLOCK_PI`: мьютексы с наследованием приоритета для реального времени. Здесь ядро уже знает владельца.
- `FUTEX_WAKE_OP`: атомарно изменить второе слово и разбудить по условию.
- `futex_waitv` (Linux 5.16): ждать на нескольких адресах сразу, сделан для Wine и игр.

## Аналоги на других системах

| Система | Примитив |
|---|---|
| Linux | `futex(2)` |
| Windows | `WaitOnAddress` / `WakeByAddressSingle` / `WakeByAddressAll` (с Windows 8) |
| macOS | недокументированный `__ulock_wait` / `__ulock_wake`, на нём libc++ и `os_unfair_lock` |
| FreeBSD | `_umtx_op` |
| OpenBSD | `futex(2)` с 6.2 |

В домашке на macOS `internal/futex` эмулирует Wait/Wake поверх карты каналов под `sync.Mutex`, чтобы код собирался везде.

## Где futex в рантайме Go

Рантайм Go на Linux паркует **потоки ОС (M)** через futex: `runtime.futexsleep` и `runtime.futexwakeup` в `runtime/os_linux.go`, поверх них `notesleep`/`notewakeup`. Это используется, когда M нечего делать, и для внутреннего `runtime.mutex`.

**Горутины** на futex не спят. Их парковка это `gopark`: горутина снимается с M и кладётся в очередь ожидания внутри рантайма, а M идёт исполнять другую горутину. `sync.Mutex` спит через `runtime_SemacquireMutex`, семафор рантайма на `sudog`-очередях, а не через syscall. Поэтому блокировка горутины на мьютексе стоит сотни наносекунд, а не микросекунды переключения потока. См. [[goroutine scheduler]] и [[sync.Mutex internals]].

## Три состояния мьютекса

Классический разбор из статьи Дреппера «Futexes Are Tricky»: мьютексу на futex нужны состояния «свободен», «занят», «занят и есть спящие». Без третьего состояния каждый `Unlock` вынужден делать syscall `WAKE` на всякий случай, и быстрый путь перестаёт быть быстрым. Подробно в [[mutex]].
