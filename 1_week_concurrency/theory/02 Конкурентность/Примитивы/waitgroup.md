# WaitGroup

Счётчик незавершённой работы. `Add(n)` увеличивает его, `Done` уменьшает на один, `Wait` блокирует, пока счётчик не станет нулём. Классический сценарий: запустили N горутин, дождались, пока все закончат.

В отличие от [[mutex|мьютекса]] и [[semaphore|семафора]] здесь нет ресурса, который делят. Ждущим нужен один и тот же момент, «всё закончилось», поэтому тот, кто довёл счётчик до нуля, будит **всех** сразу.

Связанные заметки: [[mutex]], [[semaphore]], [[barrier]], [[atomic]], [[go memory model]], [[errgroup]].

## Устройство

Одно слово `count uint32`, все операции атомарные, сон через [[mutex#Что такое futex|futex]].

### Add

1. `AddUint32(&count, uint32(delta))`. Отрицательная delta заворачивается по модулю 2³², а сложение по модулю даёт тот же результат, что и вычитание. Поэтому один атомик покрывает и `+n`, и `-1`.
2. Результат читаем как `int32`. Если он отрицательный, счётчик ушёл в минус: `Done` без `Add`. Паника.
3. Если результат ноль, работа закончена: `futex.WakeAll(&count)`.

### Done

`Add(-1)`. Отдельной логики нет.

### Wait

Цикл:
1. `LoadUint32(&count)`. Ноль → возвращаемся сразу.
2. Иначе `futex.Wait(&count, c)`, где `c` это **только что прочитанное** значение. После пробуждения снова на шаг 1.

> [!warning] Спать на прочитанном значении, а не на «не ноль»
> Между «прочитали c ≠ 0» и «уснули» счётчик могли обнулить, и `WakeAll` отгремел бы без нас. Аргумент `c` в `Wait` закрывает дыру: если значение уже другое, ядро возвращает управление сразу, цикл перечитывает счётчик и видит ноль.

## Почему WakeAll, а не Wake

У мьютекса после `Unlock` войти сможет один, поэтому будят одного, остальные всё равно снова уснут. У WaitGroup после обнуления **все** ждущие вправе идти дальше, каждый ждал одного и того же события. Будить по одному пришлось бы цепочкой, и это медленнее и сложнее.

## Гарантии видимости

Go memory model обещает: всё, что горутина сделала до `Done`, видно тому, кто вернулся из `Wait`. Формально `Done` *synchronizes before* возвратом `Wait`. Это следствие того, что атомики в Go последовательно согласованы (*sequentially consistent*): запись в счётчик перед `WakeAll` и чтение его в `Wait` образуют пару, через которую результаты работы горутин становятся видны без дополнительных мьютексов.

## Ловушки использования

> [!danger] Add внутри горутины
> ```go
> for i := 0; i < n; i++ {
>     go func() {
>         wg.Add(1) // поздно
>         defer wg.Done()
>         work()
>     }()
> }
> wg.Wait() // может увидеть 0 раньше, чем горутины стартуют
> ```
> `Add` должен быть **до** `go`. Иначе `Wait` может вернуться с нулевым счётчиком до того, как планировщик запустит хоть одну горутину.

> [!danger] Копирование
> WaitGroup хранит счётчик по значению. Передавать её в функцию нужно по указателю, иначе `Done` уменьшит копию, а `Wait` на оригинале будет ждать вечно. `go vet` ловит это через проверку `copylocks`.

> [!danger] Повторное использование до возврата Wait
> Если `Add` для следующего раунда вызван, пока ждущий предыдущего раунда ещё не вышел из `Wait`, он может проспать обнуление и застрять на новом значении. Стандартный `sync.WaitGroup` для этого держит число ждущих в том же 64-битном слове и паникует с «WaitGroup is reused before previous Wait has returned». В версии на одном слове это правило остаётся на совести вызывающего: новый раунд начинают только после того, как все `Wait` вернулись.

> [!danger] Done в горутине без recover
> Если горутина паникует до `Done`, `Wait` не вернётся никогда. Ставить `defer wg.Done()` первой строкой.

## Как устроен sync.WaitGroup

Стандартная реализация хранит в одном `atomic.Uint64` счётчик (старшие 32 бита) и число ждущих (младшие 32 бита), а рядом семафор рантайма `runtime_Semacquire`/`runtime_Semrelease`. Ждущие помещаются в очередь `sema` внутри рантайма, а не в futex напрямую. Идея та же: один атомик, ждущие спят, последний `Done` будит всех. Плюс паники на переиспользование и на отрицательный счётчик. С Go 1.25 появился `wg.Go(func())`, который делает `Add(1)` и `Done` за тебя.

## Альтернативы

- **`errgroup.Group`** из `golang.org/x/sync`: WaitGroup плюс первая ошибка плюс отмена контекста. В прикладном коде чаще нужен именно он. См. [[errgroup]].
- **Канал и `close`**: для одного ждущего и одной горутины хватает `done := make(chan struct{})` и `close(done)`. Ждать N горутин через канал уже неудобно.
- **[[barrier|Барьер]]**: WaitGroup, который переиспользуется по раундам и где ждут сами участники.

## Атомики и futex для этой задачи

| Функция | Где |
|---|---|
| `atomic.AddUint32(&wg.count, uint32(delta))` | `Add`: изменить счётчик и узнать новое значение |
| `atomic.LoadUint32(&wg.count)` | `Wait`: прочитать счётчик перед сном |
| `futex.Wait(&wg.count, c)` | `Wait`: уснуть на прочитанном значении |
| `futex.WakeAll(&wg.count)` | `Add`: разбудить всех при достижении нуля |
