# Once

Выполнить функцию ровно один раз, сколько бы горутин её ни попросили. Классический пример: ленивая инициализация. Соединение с базой, разбор конфига, построение таблицы, синглтон.

Связанные заметки: [[mutex]], [[waitgroup]], [[atomic]], [[go memory model]], [[sync.OnceValue]].

## Почему наивный вариант сломан

```go
if !done {
    done = true
    f()
}
```

Три ошибки сразу:
1. **Гонка данных.** `done` читают и пишут без синхронизации. По Go memory model это неопределённое поведение, `go test -race` укажет на него.
2. **Двойной вход.** Две горутины могут прочитать `false` одновременно, обе поставят `true`, обе вызовут `f`.
3. **Ранний возврат.** Самое коварное. Вторая горутина видит `done == true`, возвращается и идёт работать с состоянием, которое первая ещё строит. Флаг «начали» и флаг «закончили» это разные вещи.

Из третьего пункта следует главное требование: **проигравшие гонку ждут**, пока победитель закончит, и только потом возвращаются.

## Три состояния

| значение | смысл |
|---|---|
| `notStarted` (0) | никто ещё не начинал |
| `running` (1) | победитель гонки выполняет `f`, остальные ждут |
| `done` (2) | `f` отработала или упала, больше не запускаем |

Двух состояний мало ровно по третьей причине выше: между «начали» и «закончили» есть окно, в котором остальным нужно спать, а не проходить.

## Алгоритм Do

1. **Быстрый путь.** `Load == done` → возврат. Сюда попадают все вызовы после первого, поэтому тут одно атомарное чтение и ничего больше. Это и есть правильный *double-checked locking*.
2. **Гонка.** `CAS(notStarted → running)`. Выигрывает ровно одна горутина.
3. **Победитель.** Вызывает `f`, затем `Store(done)` и `futex.WakeAll`. Переход в `done` и побудка стоят в `defer`, чтобы сработать и при панике.
4. **Проигравшие.** Цикл: пока `Load != done`, `futex.Wait(&state, running)`. Спим на значении `running`, и если победитель уже успел поставить `done`, ядро вернёт нас сразу.

Будим через `WakeAll`, как в [[waitgroup]]: всем ждущим нужен один и тот же момент.

## Паника в f

Что делать, если `f` упала посередине? Два варианта:

- **Считать вызов состоявшимся** и больше `f` не запускать. Так делает `sync.Once`. Логика: следующий вызывающий иначе получит наполовину проинициализированное состояние, а повторный запуск `f` поверх мусора редко бывает безопасен.
- **Откатить в `notStarted`** и дать следующему попробовать снова. Так ведёт себя `std::call_once` в C++.

В Go принят первый вариант. Реализация: `defer` с переходом в `done` и побудкой. Паника при этом не глотается, а уходит дальше к тому, кто вызвал `Do`, но `Once` уже считается сработавшим, и ждущие не зависают.

## Гарантии видимости

Go memory model: возврат из `Do` *synchronizes after* завершением `f`. Всё, что `f` записала, видно любой горутине после её `Do`, даже той, что вернулась по быстрому пути через одно атомарное чтение. Это работает, потому что `Store(done)` победителя и `Load` читающего образуют пару последовательно согласованных атомарных операций.

## Double-checked locking

Паттерн из 1990-х: проверить флаг без замка, если не готово, взять замок, проверить снова, инициализировать. В Java до версии 5 и в C++ до C++11 он был **сломан**: без барьеров памяти процессор или компилятор мог сделать запись флага видимой раньше, чем записи самого объекта. Читатель видел `done == true` и недостроенный объект.

Правильная версия требует атомарного чтения флага с семантикой *acquire* и атомарной записи с семантикой *release*. В Go все операции `sync/atomic` дают это автоматически, поэтому `Load` в быстром пути и `Store(done)` после `f` образуют корректную пару.

## Как устроен sync.Once

```go
type Once struct {
    done atomic.Uint32
    m    Mutex
}
```

Быстрый путь: `done.Load() == 0`, иначе возврат. Медленный путь: захват мьютекса, повторная проверка `done`, `defer done.Store(1)`, вызов `f`. Ждущие спят на мьютексе, а не на futex напрямую, поэтому отдельного состояния `running` нет: его роль играет захваченный мьютекс. Обратите внимание, что в стандартной библиотеке не пишут `CAS(0 → 1)` до вызова `f`: тогда быстрый путь мог бы вернуться до окончания работы.

С Go 1.21 есть обёртки: `sync.OnceFunc(f)` возвращает функцию, которая вызовет `f` один раз, `sync.OnceValue(f)` кеширует результат, `sync.OnceValues` для пары значений. Они же по-другому обращаются с паникой: запоминают её и повторяют при каждом вызове. См. [[sync.OnceValue]].

## Ловушки

> [!danger] Рекурсивный Do
> Если `f` сама вызывает `o.Do` на том же `Once`, это дедлок: внутренний вызов будет ждать завершения внешнего.

> [!danger] Копирование
> Как и остальные примитивы `sync`, `Once` нельзя копировать после первого использования. Передавать по указателю.

> [!warning] Once не для повторной инициализации
> Сбросить `Once` нельзя. Если ресурс нужно пересоздавать, например переподключаться к базе, `Once` не подходит: нужен мьютекс и явное состояние.

## Атомики и futex для этой задачи

| Функция | Где |
|---|---|
| `atomic.LoadUint32(&o.state)` | быстрый путь `Do`, цикл ожидания, весь `Done` |
| `atomic.CompareAndSwapUint32(&o.state, notStarted, running)` | гонка за право выполнить `f` |
| `atomic.StoreUint32(&o.state, done)` | победитель после `f`, в `defer` |
| `futex.WakeAll(&o.state)` | победитель после `Store(done)` |
| `futex.Wait(&o.state, running)` | проигравшие, пока состояние не `done` |
