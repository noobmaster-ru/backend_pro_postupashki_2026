# sync.Map

Потокобезопасная мапа из стандартной библиотеки. Появилась в Go 1.9 для конкретных сценариев рантайма, и документация честно говорит: **в большинстве случаев лучше обычная `map` с мьютексом**.

Связанные заметки: [[rwmutex]], [[atomic]], [[RCU]], [[mutex]], [[cache coherence]].

## Когда она уместна

Документация называет два случая:

1. **Ключ пишется один раз, читается много.** Кеши, реестры, таблицы по типам. Пример из рантайма: `reflect` кеширует тип → метаданные.
2. **Разные горутины работают с непересекающимися наборами ключей.** Каждая горутина пишет свои ключи, чужие не трогает.

В этих случаях `sync.Map` масштабируется на много ядер лучше, чем `map + RWMutex`, потому что чтения не пишут в общую кеш-линию. Во всех остальных случаях (частые записи по одним ключам, нужна типобезопасность, нужен размер) `map + sync.Mutex` проще и не медленнее.

## API

| Метод | Смысл |
|---|---|
| `Load(k)` | прочитать, `ok` если есть |
| `Store(k, v)` | записать |
| `LoadOrStore(k, v)` | атомарно: вернуть существующее или записать |
| `LoadAndDelete(k)` | атомарно: прочитать и удалить |
| `Delete(k)` | удалить |
| `Swap(k, v)` | заменить, вернуть старое (1.20) |
| `CompareAndSwap(k, old, new)`, `CompareAndDelete(k, old)` | условные операции (1.20) |
| `Range(f)` | обход; не снимок, может видеть изменения по ходу |
| `Clear()` | очистить (1.23) |

Ключи и значения типа `any`: нет типобезопасности, интерфейсное упаковывание на каждой операции, нет `Len`. Обычно `sync.Map` оборачивают в свой типизированный тип.

## Классическая реализация (до Go 1.24)

Две мапы и счётчик промахов:

```go
type Map struct {
    mu     Mutex
    read   atomic.Pointer[readOnly] // map[any]*entry + флаг amended
    dirty  map[any]*entry
    misses int
}
```

- **read**: неизменяемая мапа, читается без замка через атомарный указатель. Значения хранятся через `*entry`, внутри атомарный указатель на значение, поэтому **обновить существующий ключ можно без замка** CAS'ом внутри entry.
- **dirty**: полная мапа под мьютексом, содержит всё из read плюс новые ключи. Флаг `amended` в read говорит, что в dirty есть что-то, чего нет в read.
- **Промах**: ключа нет в read, но `amended` → берём мьютекс, ищем в dirty, увеличиваем `misses`. Когда `misses >= len(dirty)`, dirty целиком становится новым read, dirty обнуляется. Так новые ключи со временем «продвигаются» в быстрый путь.
- **Удаление**: entry помечается `nil`, при следующем продвижении `expunged`, чтобы не копировать удалённые ключи в новый dirty.

Именно поэтому сценарий «записал раз, читаешь много» идеален: после первого продвижения все чтения идут по read без замка, а обновления значений идут CAS'ом по entry. И поэтому сценарий с постоянными новыми ключами плох: каждая вставка под мьютексом, плюс периодическое копирование dirty.

## Реализация с Go 1.24: HashTrieMap

В Go 1.24 `sync.Map` переписан поверх `internal/sync.HashTrieMap`: конкурентное хеш-дерево (*hash-array mapped trie*). Узлы дерева неизменяемы или защищены мелкозернистыми мьютексами, чтения без замков через атомарные указатели, вставки и удаления блокируют только один узел. Результат: нет фазы продвижения dirty → read, нет деградации на вставках новых ключей, лучше масштабирование записей. Старое поведение можно вернуть через `GOEXPERIMENT=nosynchashtriemap`. Семантика API не изменилась. Тот же HashTrieMap лежит под `unique.Make` в Go 1.23+.

## Альтернативы

| Вариант | Когда |
|---|---|
| `map + sync.Mutex` | по умолчанию. Просто, типобезопасно, быстро без сильной конкуренции |
| `map + sync.RWMutex` | много читателей с долгими чтениями. При коротких чтениях проигрывает, см. [[rwmutex]] |
| Шардированная мапа | N мап, каждая со своим мьютексом, ключ выбирает шард по хешу. Хорошо масштабирует и чтения, и записи |
| `atomic.Pointer` на неизменяемую мапу | редкие записи, чтения без замка вообще. См. [[RCU]] |
| `sync.Map` | два случая из документации |

## Ловушки

> [!warning] Range не снимок
> Обход может увидеть часть изменений, сделанных параллельно, и может не увидеть другие. Если нужен согласованный снимок, нужен свой замок или copy-on-write.

> [!warning] Нет Len
> Посчитать элементы можно только через `Range`, и результат мгновенно устаревает.

> [!warning] Копирование
> Как и остальное в `sync`, после первого использования копировать нельзя.
