# Worker pool

Фиксированное число горутин читает задачи из общего канала и пишет результаты. Цель в Go не в экономии на создании горутин, они дешёвые, а в **ограничении параллелизма**: не больше N одновременных запросов к базе, не больше N открытых файлов, не больше N мегабайт в обработке.

Связанные заметки: [[channels]], [[waitgroup]], [[errgroup]], [[semaphore]], [[goroutine scheduler]].

## Каноническая форма

```go
func process(ctx context.Context, items []Item, workers int) ([]Result, error) {
    jobs := make(chan Item)
    results := make(chan Result, len(items)) // буфер, чтобы воркеры не зависли на записи

    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for it := range jobs {          // выход при закрытии jobs
                results <- handle(ctx, it)
            }
        }()
    }

    for _, it := range items {
        select {
        case jobs <- it:
        case <-ctx.Done():
            break // выйти из цикла отправки
        }
    }
    close(jobs)   // сигнал воркерам: больше не будет
    wg.Wait()     // дождаться всех
    close(results)

    var out []Result
    for r := range results { out = append(out, r) }
    return out, ctx.Err()
}
```

Обязательные элементы:
1. **`close(jobs)`** делает отправитель после последней задачи. Без него воркеры висят в `range` навсегда.
2. **`WaitGroup`** с `Add` до `go`, см. [[waitgroup]].
3. **`close(results)` после `wg.Wait()`**, иначе кто-то запишет в закрытый канал. Если результаты читаются параллельно, `wg.Wait(); close(results)` уходит в отдельную горутину.
4. **Контекст** для отмены: проверять в отправке задач и внутри `handle`.

## Три способа ограничить параллелизм

| Способ | Когда |
|---|---|
| Пул из N воркеров и канал задач | задач много, воркеру нужно состояние: соединение, буфер, клиент |
| Семафор: буферизованный канал или `x/sync/semaphore`, горутина на задачу | задач не очень много, состояние не нужно; проще, чем пул |
| `errgroup` с `SetLimit(N)` | нужна первая ошибка и отмена остальных. См. [[errgroup]] |

Семафорный вариант в две строки:

```go
sem := make(chan struct{}, n)
for _, it := range items {
    sem <- struct{}{}
    go func() { defer func() { <-sem }(); handle(it) }()
}
```

Пул из N воркеров это тот же семафор, только разрешения привязаны к живым горутинам. Выбирать пул стоит, когда у воркера дорогая инициализация или задач миллионы и создавать по горутине на каждую расточительно по памяти.

## Сколько воркеров

- **CPU-bound**: `runtime.GOMAXPROCS(0)`. Больше не даст ускорения, только переключения.
- **IO-bound**: столько, сколько выдержит внешняя система: размер пула соединений к базе, лимит запросов в секунду у API, число дисков. Обычно подбирается измерением.
- **Смешанная нагрузка**: разделить на стадии с разным числом воркеров, это pipeline.

## Ловушки

> [!danger] Результаты без читателя
> Воркеры пишут в `results`, а читать его начнут только после `wg.Wait()`. Если буфер меньше числа задач, дедлок. Либо буфер на все задачи, либо читать параллельно из отдельной горутины.

> [!danger] Паника в воркере
> Роняет весь процесс. Если задачи приходят снаружи и могут быть кривыми, `recover` внутри воркера с логированием и продолжением.

> [!danger] Захват переменной цикла
> До Go 1.22 `for i := ...; go func() { use(i) }()` видел последнее значение. С Go 1.22 у каждой итерации своя переменная. В старом коде передавать аргументом.

> [!warning] Отмена без выхода воркеров
> `ctx.Done()` внутри `handle` прерывает текущую задачу, но воркер вернётся в `range jobs` и будет ждать. Отправитель обязан закрыть `jobs` и при отмене тоже, иначе утечка.

> [!warning] Порядок результатов
> Не совпадает с порядком задач. Если нужен порядок, писать результат в `out[i]` по индексу задачи, а не в канал.

> [!warning] Backpressure
> Небуферизованный `jobs` это хорошо: производитель замедляется до скорости потребителей. Огромный буфер скрывает проблему, пока не кончится память.

## Динамические пулы

Когда нагрузка скачет, воркеров запускают по мере надобности и останавливают по простою. Библиотеки: `panjf2000/ants`, `sourcegraph/conc` (пул с ограничением и сбором ошибок, `conc.WaitGroup` с перехватом паник). В большинстве сервисов достаточно `errgroup.SetLimit`.
