# Каналы

Типизированная очередь с встроенной синхронизацией. Единственный примитив конкурентности, встроенный в язык, остальное живёт в `sync`. Лозунг из Effective Go: *«Don't communicate by sharing memory; share memory by communicating.»*

Связанные заметки: [[goroutine scheduler]], [[go memory model]], [[semaphore]], [[worker pool]], [[errgroup]], [[mutex]].

## Семантика операций

| Операция | nil-канал | открытый | закрытый |
|---|---|---|---|
| `ch <- v` | блок навсегда | пишет или блок | **паника** |
| `<-ch` | блок навсегда | читает или блок | нулевое значение, `ok == false` |
| `close(ch)` | **паника** | закрывает | **паника** |

Из таблицы следуют правила:
- Закрывает **отправитель**, и только один. Получатель закрывать не может: он не знает, не пишет ли кто-то ещё.
- Блокировка на nil-канале это фича: в `select` присвоить каналу `nil`, чтобы выключить ветку.
- `for v := range ch` читает до закрытия, это идиоматичный способ дождаться конца потока.
- `v, ok := <-ch` отличает «прислали ноль» от «закрыли».

## Небуферизованный и буферизованный

**Небуферизованный** (`make(chan T)`): отправка завершается только когда получатель забрал значение. Это **рандеву**: точка синхронизации в обе стороны. По [[go memory model]] приём *happens before* завершение отправки, и отправка *happens before* завершение приёма.

**Буферизованный** (`make(chan T, n)`): отправка блокируется только при полном буфере, приём при пустом. Синхронизация слабее: k-й приём *happens before* завершение (k+n)-й отправки. Буфер сглаживает всплески, но **не** увеличивает пропускную способность, если потребитель стабильно медленнее.

Буферизованный канал ёмкости n это готовый [[semaphore]] на n разрешений: `sem <- struct{}{}` берёт, `<-sem` отдаёт.

## Устройство: hchan

```go
type hchan struct {
    qcount   uint           // элементов в буфере
    dataqsiz uint           // ёмкость буфера
    buf      unsafe.Pointer // кольцевой буфер
    elemsize uint16
    closed   uint32
    sendx    uint           // индекс записи в кольце
    recvx    uint           // индекс чтения
    recvq    waitq          // очередь спящих получателей (sudog)
    sendq    waitq          // очередь спящих отправителей
    lock     mutex          // мьютекс рантайма
}
```

Все операции идут под `lock`. Канал это **мьютекс плюс кольцевой буфер плюс две очереди ожидания**. Никакой магии lock-free.

**Отправка** (`chansend`):
1. Есть спящий получатель в `recvq` → копируем значение **прямо в его стек**, будим через `goready`. Буфер не трогаем. Это единственное место в рантайме, где одна горутина пишет в стек другой.
2. Иначе есть место в буфере → кладём в `buf[sendx]`.
3. Иначе создаём `sudog`, встаём в `sendq`, `gopark`. Проснёмся, когда получатель заберёт значение из нашего sudog.

**Приём** симметричен: спящий отправитель в `sendq` → забрать у него напрямую (если буфер полон, взять из головы буфера, а его значение положить в хвост). Иначе из буфера. Иначе спать в `recvq`.

**close**: под замком выставить `closed`, разбудить всех в `recvq` (они получат ноль и `ok=false`) и всех в `sendq` (они запаникуют).

Стоимость операции без конкуренции: захват мьютекса рантайма, копирование элемента, порядка 50–100 нс. Медленнее, чем `sync.Mutex` на простом счётчике, потому что делает больше.

## select

Ждёт на нескольких каналах сразу.
- Если готовы несколько веток, выбирается **случайная равновероятно**, чтобы не голодали.
- `default` делает неблокирующую попытку.
- Реализация: каналы блокируются в порядке адресов (чтобы не было дедлока между двумя select'ами), проверяются все ветки, если ни одна не готова, горутина встаёт в очереди **всех** каналов одним `sudog` на каждый, а после пробуждения снимается с остальных.
- `select {}` без веток блокирует навсегда.

## Паттерны

- **Done-канал / context**: `close(done)` как широковещательный сигнал всем читателям сразу. Сейчас почти всегда через `context.Context`.
- **Pipeline**: стадии, соединённые каналами, каждая закрывает свой выход.
- **Fan-out / fan-in**: несколько горутин читают один канал; результаты сливаются в один канал через `WaitGroup` и `close` после `Wait`. См. [[worker pool]].
- **Семафор**: буферизованный канал.
- **Генератор**: функция возвращает `<-chan T` и пишет из горутины.
- **Timeout**: `select` с `time.After` или `ctx.Done()`.
- **Ограничение направления в сигнатуре**: `chan<- T` и `<-chan T` документируют намерение и ловят ошибки на компиляции.

## Ловушки

> [!danger] Утечка горутины
> Горутина, навсегда заблокированная на отправке в канал, который никто не читает, живёт до конца процесса вместе со своим стеком и всем, на что ссылается. Классика: worker пишет результат, а вызывающий уже вышел по таймауту. Лечится буфером на 1, `select` с `ctx.Done()` или гарантией, что читатель дочитает.

> [!danger] Паника при записи в закрытый канал
> Если отправителей несколько, закрывать может только тот, кто знает, что все закончили: обычно через `WaitGroup` и отдельную горутину `wg.Wait(); close(ch)`.

> [!warning] Канал не заменяет мьютекс
> Для защиты структуры данных, к которой обращаются из многих мест, мьютекс проще и быстрее. Каналы для передачи владения данными и для сигналов между горутинами.

> [!warning] Deadlock detector
> `fatal error: all goroutines are asleep - deadlock!` срабатывает только когда **все** горутины спят. Если хоть одна крутится или ждёт сеть, зависшие каналы не обнаружатся.
